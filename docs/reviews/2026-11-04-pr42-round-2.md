## Review round 2: heinzelwerk#42 (`fix/workspace-shakedown`, focus 75bc97e)

I only read and ran things; nothing in the worktree was edited. `bash -n` is clean on all 7 scripts, and `check-note-test.sh` passes (34 cases, 0 bad). Line numbers are worktree file lines.

### Findings

**1. BLOCKER: a `task` line has no blocked-by, so the coordinator starts blocked work at once.**
- Where: team-modes/SKILL.md:38 (the line format has no blocked-by field) and coordinator/SKILL.md:34 ("apply each line at once, then spawn or resume the owner it names").
- What goes wrong: tech-lead's seed creates these blocked tasks, and each gets its owner started immediately:
  - `#N validate: slice acceptance`, blocked by every implement task (tech-lead.md:27): validator starts before any PR exists.
  - `tech-lead apply` (tech-lead.md:28).
  - Consumer tasks blocked by their provider.
  - `validate: merge`, blocked by docs validation (tech-lead.md:55).
- The snapshot has a `blocked-by` column (coordinator:114), but no rule fills it from the line or says what unblocks a task. No role has a rule for "spawned on a blocked task".
- Fix: line becomes `task create: <title> | <owner> | <branch> | blocked-by <titles or -> | <detail>`. Coordinator spawns or resumes an owner only when every blocker is `done` in the snapshot, and re-checks blocked rows on every `task done`.

**2. MAJOR: there is no claim verb, and tasks have no id.**
- team-modes:38 lists "claim" as a task operation, but the verbs are only create|done|abandon|propose|drop. Nothing moves a snapshot row to in progress.
- The snapshot wants an `id` (coordinator:114), and tech-lead says `tasks created: <ids>` (tech-lead.md:63), but lines carry no id.
- Fix: coordinator marks a row in progress when it spawns or resumes the owner, and "claim" is dropped from the list. State that the task title is the id.

**3. MAJOR: a validator fail has nowhere to put its repro or its done note.**
- validator.md:124: a fail creates the fix task with the repro "in its details", and no PR comment is posted.
- team-modes:39 says tech-lead writes validator's tasks into the plan comment, but nobody tells tech-lead. Validator cannot message tech-lead (team-modes:36 allows only product and tech-lead to message each other).
- team-modes:40 says validator's done note goes "in its verdict", but a fail posts no verdict.
- So the owner is resumed with a one-line detail and no repro.
- Fix: in hand-back mode, validator posts the fail verdict (repro plus done note) as a PR comment, and the `task create` line links it. That comment is the fix task's details. Drop "or validator opens" from team-modes:39.

**4. MAJOR: "message coordinator, then unlock" cannot be done in this order.**
- phased-workflow:85 says to message coordinator, then unlock the worktree. In hand-back mode that message is the hand-back, which ends the run, so the worktree stays locked.
- The fix round's "lock the worktree again" (phased-workflow:87, team-modes:56) then hits git's "already locked" error.
- Fix: in hand-back mode, unlock the worktree before the hand-back.

**5. MAJOR: the crash rules contradict each other.**
- team-modes:41: any API error in a hand-back means respawn `<role>-N` at once.
- coordinator:82: a usage or rate limit error means never respawn; stop the run.
- coordinator:86-89: first send one retry message. Only then spawn a replacement, after tech-lead abandons and recreates the task, which in hand-back mode means `task abandon` and `task create` lines and a plan-comment row. Without that row the replacement's spawn prompt has no task row.
- Fix in team-modes:41: "an API error in a hand-back → coordinator §3 Usage limit / Failure rules; spawn `<role>-N` after tech-lead's abandon and create lines."

**6. MAJOR: the run-start match is fragile and the coordinator's rules contradict each other.**
- coordinator:17 prescribes a `run start: <ts>` line. coordinator:116 says every timestamp in the run state is "marked `UTC`".
- Tested against the sed + `grep -qxF` at spawn-context:162:

  | Line in run state | Label |
  |---|---|
  | `- run start: 2026-11-04T22:39:35Z` | this run |
  | `* run start: …  ` (trailing spaces) | this run |
  | `run start: 2026-11-04T22:39:35Z UTC` | an earlier run |
  | `**run start:** …` | an earlier run |
  | `- **run start**: …` | an earlier run |
  | backticked ts | an earlier run |
  | table row | an earlier run |
  | `Run start:` | an earlier run |

  `--start` carrying " UTC" also mislabels.
- So the coordinator's format does not guarantee a match: following line 116 breaks it.
- In hand-back mode the run state is the live task list, so this mislabel tells teammates their live list belongs to an earlier run.
- A resumed run gets a new run start, so its own state is labelled "earlier" too.
- Fix:
  - coordinator:116: exempt this line ("the `Z` is the UTC mark") and give the literal line.
  - spawn-context: strip `*` and backticks anywhere, compare case-insensitively, and allow a trailing ` UTC`.
  - On resume, coordinator rewrites the `run start:` line.

**7. MAJOR: the main-only acceptance is not tied to the head or the check, and its trigger fails open (merge-gate:59-62).**
- Any line starting `heinzelwerk: accepted main-only ` clears it: from any comment, for any check, any sha, any earlier head. A fix round that changes the code behind that check keeps the old acceptance.
- The trigger needs the exact phrase `inconclusive: runs on main only`. A validator who writes "inconclusive: job runs only on main" skips the gate entirely, and `check-note verdict` does not enforce the wording.
- Can a validator or implementer comment satisfy it? Yes, under the shared login. That is acceptable under ADR 0001, which already treats the validated line as a protocol marker, not an authorization. But ADR 0001's Consequences should name the new marker, and the marker should be at least as strict as the validated line, which is sha-bound.
- Fix:
  - Parse `accepted main-only <check> @ <sha>`, require the sha to prefix-match head (reuse the line-53 loop), and require one acceptance per inconclusive check name.
  - Make `check-note verdict` reject any `inconclusive:` line that mentions main or CI but isn't the canonical form.
  - Add a regression test.

**8. MINOR: `-C` argument handling in merge-gate (lines 16-17).** Tested:
- `merge-gate -C` exits 1 with only `2: repo dir`, and `-C .` without a PR exits 1 with `1: pr number`. Neither prints a verdict line; validator.md:152 recovers by rerunning, but the header says "exit 0 either way".
- `-C /nonexistent 5` correctly prints `MERGE SKIP: no repo dir`.
- `merge-gate 5 -C dir` silently ignores `-C` and runs in cwd. At the workspace root that gives a misleading "no merge-policy.json on main".
- `$(dirname "$0")/review-gate` breaks after `cd` if the script was called by a relative path. It fails closed as a gate error.
- No tests cover `-C` or the main-only rule.
- Fix: guard argument count and a numeric PR with a `MERGE SKIP: usage` line, reject extra arguments, and resolve the script dir before `cd`.

**9. NIT: `pv comments,reviews` runs twice (merge-gate:53, :59).** One extra GraphQL call, negligible cost. Fetch `bodies` once and use it for both checks.

**10. MINOR: check-note `checks:` parsing.** Tested on a scratch copy:

**13. MINOR: run-state edit cadence (question 5).**
- No collision with the PATCH-by-id rule: only coordinator writes, and each PATCH replaces the full body from a file. The rate is far below GitHub's secondary limits (~80 writes/min); a seed hand-back carries about 8 lines.
- But "apply each line at once" reads as one PATCH per line. Say one PATCH per hand-back.
- There is no rule to find the comment id again after compaction, and in hand-back mode that id is the task list. Add a lookup by heading taking `.id` (the same query as `newest()`).
- Tech-lead's plan-comment edits (team-modes:39) need the same PATCH-by-id rule (`--edit-last` hazard, coordinator:110), and none is stated.
- The growing plan comment (done when, seams and fix rows on every task) is capped at 80 lines by spawn-context:158. The Tasks section is last, so it is cut first.

**15. MINOR: detection (team-modes:35).**

**16. NIT: two hold-back rules that don't match.**
- An uncovered PR holds back every PR after it (tech-lead.md:55).
- A skipped PR holds back only its `Depends on` consumers, the closing PR and the docs PRs (validator.md:150).
- A dependency through a held-back PR (C depends on B, B depends on the skipped A) isn't covered, because B is held back, not skipped.
- Fix: "every PR that depends on it, directly or through a held-back PR."
